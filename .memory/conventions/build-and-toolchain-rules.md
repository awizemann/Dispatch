From kickoff standard §11. Dispatch is macOS-only, but explicit -destination remains mandatory. The detached dev copy matters double here: we dogfood Dispatch on its own repo, so the dev build must never collide with a "production" copy managing the same projects. Reconciled 2026-07-29 against the post-pivot `scripts/` (build.sh = Release compile check then Debug build+test on isolated DerivedData `/tmp/dispatch-ci-dd`, DEVELOPER_DIR pinned to Xcode-beta; build-detached.sh; SIGNING.md) — pre-pivot suite/lock-file names below are kept as the WHY, not as current targets.

## Observations
- [convention] Always pass -project/-workspace, -scheme, -destination explicitly to xcodebuild — never rely on default discovery #xcodebuild
- [gotcha] Never mix two build systems on one DerivedData (Xcode-beta GUI + stable CLI) — corrupts build.db with 'disk I/O error' that is NOT disk-full; CLI verification while GUI is open uses a throwaway -derivedDataPath #deriveddata
- [gotcha] After a toolchain bump, a SwiftPM dep failing with region-isolation/sending errors usually has a patch release in the current minor — bump Package.resolved; only a clean build recompiles the dep and exposes it #swiftpm
- [convention] Provide a no-argument scripts/build-detached.sh that builds into isolated DerivedData and launches a visually-distinct dev copy, quitting only its own previous copy #dogfood

- [gotcha] xcodebuild's parallel stdout MANGLES (not drops) exactly ONE "Test case … passed" line per run — interleaving truncates it mid-line (observed shapes: "est case '…'", a line fused with another's tail), arbitrary victim test each run; the mangled test DID pass. So `grep -c "passed"` undercounts by exactly 1. Judge suites by `** TEST SUCCEEDED **` + zero failed/crashed lines; pin exact counts via a NAME-LEVEL diff of extracted passed-test names between two runs (proven in a 2026-07-07 round that reconciled a phantom "+12 vs +11" delta), or the xcresult summary. ±1 vs baseline is expected noise; >1, or a named test missing in a name-diff, needs investigation. (This gotcha had been observed before.) #testing #xcodebuild

- [rule] COMMIT GATING IS STRUCTURAL: chain `./scripts/build.sh && git add … && git commit …` so the commit cannot run on a red build. Never gate via `;`-separated echo/grep steps — `echo "failed: $(grep -c …)"` exits 0 regardless of the count, and exactly that let a red suite reach commit once (2026-07-07, fixed by 2328aac). Verify greenness from the build's own exit status, then read the counts for the report #process #git
- [gotcha] MAIN-ACTOR STARVATION IN TESTS: the project builds with default MainActor isolation, so EVERY test and every store Task shares one actor — at ~900-test parallel scale, wall-clock-deadline polls (eventually/pollUntil) against timer-driven state can starve past ANY deadline while isolated runs stay green. Deterministic pattern: a #if DEBUG awaitPending…ForTesting() seam that drains the in-flight Task (no deadline to lose) — DocumentsStore.awaitPendingScanForTesting and MessagesInboxModel.awaitPendingSearchForTesting are the precedents. RESOLVED 2026-07-23 (3fa1c13): ChatStore.spawnSink now registers EVERY fire-and-forget side-effect Task in a self-reaping DEBUG registry drained by awaitSinkTasksForTesting (loops until quiescent); ScriptedAgentRuntime gained continuation-based waitForSentMessages/waitForPermissionResponses; 30 victim tests converted to settle → drain → assert; the shared waitUntil/waitForEvents default deadline rose 10s → 120s (the deadline prices only the failure path). Two consecutive full-suite greens (2,597/0, 2,596/0). RULE going forward: a new fire-and-forget Task in an @Observable store MUST ride a self-reaping DEBUG task registry drained by an await…ForTesting seam — a bare `Task {}` is invisible to the drains and re-introduces the flake class; new tests await seams, never wall-clock polls #testing #concurrency

- [gotcha] #Preview BODIES ARE TYPE-CHECKED IN RELEASE: the macro does not strip its body per configuration, so a preview (or any un-gated helper) referencing a #if DEBUG-only symbol breaks ONLY the Release build — Debug stays green and the dev loop never sees it (sat unnoticed 12 days). Rule: a DEBUG-only seam (DocumentsStore.overrideForPreview, StubDocumentScanner, AppStores.previewDocuments) must be #if DEBUG-wrapped at EVERY referencing layer, including the #Preview block itself. Un-gated previews over Release-available helpers (AppStores.mock()) are fine and are the repo norm (28 such previews). Cheap check after touching preview seams: `xcodebuild build -scheme Dispatch -destination 'platform=macOS' -configuration Release`. RECURRED: ae9f5d6 (Documents tab) shipped MockData.makeDocumentsPreviewStores + a #Preview over it un-gated; fixed 2026-07-23. AUTOMATED: scripts/build.sh now runs a Release compile as its FIRST step (before the Debug build+test), so the commit-gating chain catches this class structurally. Decision rationale: in-every-run (not a separate opt-in script — opt-in is how it shipped twice), first-not-appended (cheap incremental step fails fast, and still executes when a suite flake would red the run later), same CI DerivedData (the mixing gotcha bans two build SYSTEMS on one DerivedData, not two configurations — sharing keeps SwiftPM warm so the recurring cost is seconds, only the first run pays the ~3-4 min cold build). Negative-tested: an un-gated #Preview over a DEBUG-only symbol reds the step with 0 tests run #xcodebuild #preview



## Isolation-rerun trap: method-level -only-testing can select zero tests (2026-07-21)
`xcodebuild -only-testing:DispatchTests/Suite/testName` against a Swift Testing (not XCTest) test can match NOTHING and still print `** TEST SUCCEEDED **` — a false-isolation pass. This misclassified a deterministically red lock test as a load flake. When isolate-rerunning a failure, confirm the target test's name actually appears in the run log (it executed) before trusting the green. Corollary that outlived the pre-pivot suites: any diff touching a TOOL CATALOG or PROTOCOL TEXT surface must run ALL the lock suites, and they do not all live where you'd guess — grep `DispatchTests/` for the protocol-version and tool-catalog locks before committing rather than relying on a remembered list.



## Drain seams over deadlines + the commit-gate scoped-chain practice (2026-07-21, c97e0fc)
- [convention] Deflaking timing tests: convert the test to await the REAL pending work via a `#if DEBUG` drain seam (an `await…ForTesting()` on the store that owns the in-flight Task). A Date-deadline poll can starve past ANY deadline under parallel-suite load. Exception: pending work that genuinely PROGRESSES under load (AppKit layout passes) may keep a generous poll deadline. Task registries backing seams must SELF-REAP on completion ([UUID: Task] keyed, remove-on-finish) — an append-only array is a memory leak in live Debug sessions.
- [gotcha] The zero-select trap has a second face: Swift Testing suite STRUCT names ≠ FILE names (one file routinely holds two suite structs). `-only-testing:` with the file-derived name also selects zero and prints SUCCEEDED. Always select by struct-suite name and confirm execution by test name in the log.
- [convention] Commit gating is back to the plain full chain (`./scripts/build.sh && git add … && git commit …`) and has been since 2026-07-23 — a red full-suite run is evidence against the diff, not presumed flake. The scoped-chain carve-out (gate on the suites touching the diff + the catalog/protocol locks) is the documented fallback for a future sustained-red episode ONLY, never the default.


- [gotcha] Tool-schema literals in `DispatchEndpoint` cannot take `+`-concatenated strings INSIDE the schema: the `.object([...])` JSON-DSL literals are already at the type-checker's edge, and one multi-line `"a " + "b"` description inside them tips "unable to type-check this expression in reasonable time" (hit 2026-07-23). Keep schema description strings single-literal (long lines are fine); tool DESCRIPTION fields outside the schema literal concatenate safely — which is why the four Dispatch tools' long descriptions are `+`-joined and their inner property descriptions are not #xcodebuild #busendpoint


- [gotcha] TWO test-count methods diverge by ~160 on this suite and BOTH are right: stdout `grep -c 'Test case.*passed'` counts each parameterized-test ARGUMENT INSTANCE (~2,677 at 6b344b5); the xcresult summary counts test FUNCTIONS (~2,515 at the same tree). Cross-method comparison is meaningless — pin baselines to ONE method (repo baseline uses stdout counting) and never treat the xcresult figure as lost tests (chased and reconciled 2026-07-24, Phase 5 audit) #testing #xcodebuild
